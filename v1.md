# V1 Execution Todo

This is the practical build checklist for the first useful version of the AI-powered code audit SaaS.

V1 goal:

> A signed-in user submits a public GitHub repository and receives a web report with prioritized, evidence-backed launch-readiness findings.

## Non-Negotiable V1 Constraints

- Public GitHub repositories only.
- Static analysis only.
- Do not run repository package scripts.
- Do not run untrusted application code.
- Every AI-generated finding must be backed by scanner or metric evidence.
- Web report first; PDF can come after the report experience is solid.
- Optimize for useful top findings, not exhaustive noise.

## Phase 1: Product Skeleton

### 1. Rename Product Surfaces

- Replace starter branding with the product name.
- Update web dashboard copy for code audits.
- Remove or hide starter reference feature UI if it distracts from the product.
- Keep account/auth flows intact.

Acceptance:

- Signed-in users land on an audit-focused dashboard.
- No primary screen still looks like a generic starter.

### 2. Define Core Database Models

Add models for:

- Repository.
- Analysis job.
- Report.
- Finding.

Minimum fields:

- Repository URL.
- Repository owner/name.
- Submitted user ID.
- Job status.
- Job progress message.
- Report verdict.
- Report score.
- Finding category.
- Finding severity.
- Finding source tool.
- Finding file path.
- Finding line number.
- Finding title.
- Finding explanation.
- Finding recommendation.
- Raw metadata JSON where useful.

Acceptance:

- Prisma schema represents the full V1 report lifecycle.
- Reports and findings are owned by users.
- Deleting a user cleans up owned audit data or has explicit retention semantics.

### 3. Add Shared API Contracts

Create shared schemas for:

- Create report request.
- Report list item.
- Report detail response.
- Job status response.
- Finding response.

Acceptance:

- Web and server import the same contract types.
- Invalid GitHub URLs are rejected consistently.

## Phase 2: Report Creation Flow

### 4. Build Repository Submission UI

Add a dashboard form with:

- GitHub repository URL input.
- Submit button.
- Basic validation.
- Loading state.
- Error state.

Acceptance:

- User can submit a public GitHub URL.
- UI shows validation errors clearly.
- Successful submission navigates to report or job status page.

### 5. Add Report Creation API

Implement:

- `POST /api/reports`
- Auth requirement.
- URL validation.
- Repository normalization.
- Job row creation.
- Queue enqueue.

Acceptance:

- API creates a queued analysis job.
- User cannot create reports for another user.
- Bad URLs return stable 400 errors.

### 6. Add Report List And Detail APIs

Implement:

- `GET /api/reports`
- `GET /api/reports/:id`
- `GET /api/jobs/:id`

Acceptance:

- Users only see their own reports.
- Pending reports expose useful job status.
- Completed reports expose findings and summary.

## Phase 3: Queue And Worker

### 7. Add Redis And BullMQ

Add queue infrastructure:

- Shared queue name.
- Job payload schema.
- API producer.
- Worker consumer.
- Retry policy.
- Timeout policy.

Acceptance:

- API can enqueue an analysis job.
- Worker can consume the job locally.
- Failed jobs are marked failed with a user-safe error.

### 8. Build Worker App

Create a dedicated worker package or app.

Worker responsibilities:

- Load environment.
- Connect to database.
- Connect to Redis.
- Process analysis jobs.
- Update job status.
- Persist report results.

Acceptance:

- Worker runs independently from the API.
- API remains responsive during analysis.
- Worker shutdown does not corrupt job state.

### 9. Implement Safe Clone Step

Add repository cloning with limits:

- Only allow GitHub HTTPS URLs.
- Clone into a temporary workspace.
- Use shallow clone.
- Set timeout.
- Reject oversized repositories where feasible.
- Clean up workspace after job.

Acceptance:

- Public repos can be cloned.
- Invalid or unavailable repos fail cleanly.
- Temporary files are removed after success or failure.

## Phase 4: Static Analysis

### 10. Integrate Gitleaks

Run Gitleaks against the cloned repository.

Implementation notes:

- Output JSON.
- Redact secret values.
- Normalize into internal finding evidence.
- Mark likely real secrets as high or critical.

Acceptance:

- Hardcoded secret test fixtures are detected.
- Stored data does not include raw secret values.
- Findings include file path and line number where available.

### 11. Integrate Semgrep

Run Semgrep against the repository.

Implementation notes:

- Start with conservative rulesets.
- Output JSON.
- Normalize rule ID, severity, path, line, and message.
- Deduplicate noisy findings.

Acceptance:

- Semgrep findings appear in the report.
- Rule metadata is preserved.
- Low-value noise does not dominate top findings.

### 12. Add Dependency Vulnerability Scan

Start with JavaScript/TypeScript repositories.

Implementation options:

- OSV Scanner.
- Trivy filesystem scan.
- Lockfile-based scanner.

Rules:

- Do not run package lifecycle scripts.
- Prefer lockfile analysis.

Acceptance:

- Vulnerable dependency findings are normalized.
- Package name, installed version, vulnerable range, and advisory URL are stored when available.

### 13. Add Basic Maintainability Metrics

Compute static repository metrics:

- Largest files by line count.
- Files over threshold.
- Package/dependency count.
- Missing tests.
- Missing lockfile.
- TODO/FIXME count.
- Suspicious committed artifacts.

Acceptance:

- Metrics produce findings or report signals.
- Findings are clearly labeled as maintainability signals, not guaranteed bugs.

## Phase 5: AI Report Layer

### 14. Define Normalized Evidence Schema

Before calling AI, normalize all tool outputs into one evidence format.

Fields:

- ID.
- Category.
- Tool.
- Rule ID.
- Severity.
- Confidence.
- Path.
- Line.
- Title.
- Message.
- Metadata.

Acceptance:

- AI receives compact structured evidence.
- Raw scanner output is not passed directly unless needed.

### 15. Build AI Summary Prompt

The prompt should instruct the model to:

- Use only provided evidence.
- Prioritize top issues.
- Explain impact in plain English.
- Recommend fixes.
- Avoid unsupported claims.
- Return structured JSON.

Acceptance:

- AI output validates against a schema.
- Invalid AI output is retried or converted into a safe fallback.
- Findings without evidence are rejected.

### 16. Generate Launch Readiness Score

Implement deterministic scoring outside the AI model.

Suggested rule:

- Start at 100.
- Critical: -25.
- High: -12.
- Medium: -5.
- Low: -1.
- Cap repeated related deductions.
- Force `Do not launch` if leaked secrets are found.

Acceptance:

- Score is reproducible for the same findings.
- Verdict logic is explainable.
- UI shows why the score changed.

### 17. Persist Final Report

Store:

- Executive summary.
- Verdict.
- Score.
- Category summaries.
- Prioritized findings.
- Evidence-backed recommendations.

Acceptance:

- Completed jobs always have a report record.
- Failed AI generation does not lose raw scanner findings.

## Phase 6: Report UI

### 18. Build Report Overview Page

Show:

- Verdict.
- Score.
- Repository.
- Analysis date.
- Top 5 findings.
- Category counts.
- Job status if incomplete.

Acceptance:

- User can understand launch risk within 30 seconds.
- Pending analysis shows progress instead of a blank page.

### 19. Build Findings UI

For each finding, show:

- Severity.
- Category.
- Title.
- File path and line.
- Explanation.
- Recommendation.
- Source tool.

Acceptance:

- Findings are readable without raw scanner knowledge.
- Users can filter or scan by severity/category.

### 20. Build Report History

Show previous reports for the signed-in user.

Acceptance:

- Users can return to past reports.
- Empty state encourages submitting a repository.

## Phase 7: Verification And Hardening

### 21. Add Test Fixtures

Create small local fixture repositories for:

- Secret detection.
- Semgrep security finding.
- Vulnerable dependency.
- Maintainability issue.
- Clean repository.

Acceptance:

- Worker can run against fixtures in tests or local scripts.
- Expected findings are stable.

### 22. Add Server Tests

Cover:

- Auth required.
- URL validation.
- Report ownership.
- Job status transitions.
- Failed job handling.

Acceptance:

- Core report APIs have regression coverage.

### 23. Add Worker Tests

Cover:

- Tool-output normalization.
- Score calculation.
- AI output validation.
- Secret redaction.
- Cleanup on failure.

Acceptance:

- The risky worker logic is covered without needing real external repositories.

### 24. Add Operational Limits

Enforce:

- Max repository size.
- Max analysis duration.
- Max findings stored per tool.
- Max AI evidence payload.
- Per-user daily report limit until billing exists.

Acceptance:

- One user cannot accidentally exhaust the system.
- Huge repos fail with a clear message.

## Phase 8: Beta Readiness

### 25. Add Basic Usage Limits

Before full billing:

- Allow a small number of free reports per user.
- Track report count.
- Block or rate-limit obvious abuse.

Acceptance:

- Product can be shared with beta users without unlimited usage.

### 26. Add PDF Export Later In V1

Only add this after the web report is useful.

PDF should include:

- Executive summary.
- Verdict and score.
- Top findings.
- Detailed findings.
- Evidence appendix.

Acceptance:

- PDF looks professional enough to send to a client.
- PDF content matches the web report.

### 27. Prepare Demo Repositories

Create or identify demo repos:

- One intentionally risky repo.
- One mostly clean repo.
- One AI-generated style app with common mistakes.

Acceptance:

- Product can be demoed reliably without depending on random public repos.

## Definition Of Done For V1

V1 is done when:

- A user can sign in.
- A user can submit a public GitHub repository.
- The repository is analyzed in the background.
- The worker runs at least Gitleaks and Semgrep.
- Findings are normalized and stored.
- AI generates an evidence-backed summary.
- The report shows verdict, score, top findings, and detailed recommendations.
- Failed jobs are visible and understandable.
- Basic abuse limits exist.
- The system does not execute untrusted repository code.

## First Implementation Slice

Start with the smallest end-to-end path:

1. Add report/job/finding models.
2. Add `POST /api/reports`.
3. Add a simple dashboard form.
4. Add a worker that clones a repo and returns a fake finding.
5. Store and display the fake report.
6. Replace the fake finding with Gitleaks output.
7. Add Semgrep.
8. Add AI summary.

This avoids building disconnected pieces. The product becomes real as soon as the first queued report appears on screen.
